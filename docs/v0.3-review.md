# Review of the v0.3 CaseDesk study

Written 2026-10-22 against tag `v0.3.0` (`9c60893`). Every claim below was checked against the
published trajectories in `artifacts/v0.3/` or by replaying actions through the real HTTP
service. "Verified" means reproduced; "hypothesis" means consistent with the evidence but not
yet isolated. The v0.3 results themselves are unchanged and remain the registered record.

## What holds up

- The execution stack is real: constrained decoding → typed action → httpx → TCP → FastAPI,
  with a grader that reads server state and the commit log rather than the model's claim.
- Provenance discipline is unusually good: registration before model runs, locks, three
  training seeds reported (not the best one), all failures published, GPU-free replay.
- The grader catches what final-state checks miss. In
  `large-test/test_concurrent_injection-6302` the 1.7B model wrote a *different* ticket that
  already had the requested values; the final target state was correct, but the commit audit
  and missing fresh read fail it.

## Verified problems

**P1. The test set is three lookup problems, not 30 episodes.** All ten compositions reuse
the same three records, and the record alone determines the outcome for the trained models:

| Arm | 6301 (slot 3) | 6302 (slot 3) | 6303 (slot 0) |
|---|---:|---:|---:|
| LoRA 3407 | 10/10 | 10/10 | 0/10 |
| LoRA 42 | 10/10 | 10/10 | 10/10 |
| LoRA 2026 | 10/10 | 10/10 | 0/10 |
| 1.7B base | 7/10 | 5/10 | 0/10 |
| 4B (Ollama) | 3/10 | 3/10 | 0/10 |

This is why the template bootstrap collapsed to `[66.7, 66.7]`: there are effectively three
units, and per-record success is all-or-nothing.

**P2. The matched 0.6B baseline never reached a single fault.** In 0/30 episodes did it read
the target ticket; no 412, 429, 502 or 403 was ever exposed. Its 0/30 measures lookup and
workflow-following, so "0% → 77.8%" is mainly a lookup/workflow gain. It cannot support a
claim about recovery against the matched base.

**P3. Target position is confounded with the one-shot demo.** The shared demo's target is in
slot 3. Test records 6301/6302 also put the target in slot 3; 6303 puts it in slot 0, a slot
no training or dev record used (train slots `[3,5,1,4,4,3]`). Every model except LoRA-42
fails 6303: LoRA-3407 pages through the list three times and runs out of budget, LoRA-2026
reads `T-9925-4` (a near-miss) and claims success, the 1.7B model reads a wrong ticket in
10/10 episodes and commits writes to non-target tickets.

**P4. IDs and distractor references encode list position.** Ticket IDs are `T-dddd-{slot}` and
every distractor reference is `{ref}-{slot}`, so "the reference without a suffix" and "the ID
ending in the demo's slot" are both available shortcuts.

**P5. Grader leniency (latent).** Replayed counterexamples: (a) filing an escalation and then
resolving correctly passes, although an operator was paged for nothing; (b) escalating
*before* any denial passes if a 403 happens later. Re-grading all 180 published trajectories
with the stricter rule changes **no** verdict, so the published numbers are unaffected.

**P6. The teacher is only correct on its own state distribution.** `reference_next` treats the
most recent `get_ticket` as the target. From states where a learner read a near-miss ticket,
it patches the target with the *other* ticket's ETag or claims success: 21 of 91 such
perturbed states produced a failing label (17 false successes, 4 redundant writes). This is
harmless for v0.3 (expert-only data) but disqualifies it for any learner-state data
collection (recovery SFT, DAgger, RL reward shaping).

**P7. Dev could not detect P1/P3.** Two dev records, both with the target on page two; all
three seeds passed 8/8 dev rollouts and selected epoch 3 by dev loss.

## What the v0.3 evidence does and does not support

Supported, within this synthetic contract:

- LoRA training made the 0.6B model execute the full lookup → read → write → verify workflow
  that the base model never completed, with 100% schema-valid calls in every arm.
- On the 20 episodes where the target was found by every arm (records 6301/6302), all three
  LoRA seeds passed 20/20 fault compositions, versus 12/20 for the 1.7B base and 6/20 for the
  4B control. This is the cleanest fault-handling evidence, but it conditions on lookup
  success and compares against different (unmatched) models.

Not supported: a stable 77.8% success rate (it is two of three records, ±1 record), any claim
about recovery relative to the matched base, robustness to target position, wording or
records, or a reliability interval.

## Recommendation

Keep the service, adapter, schema, grader, locks and replay audit; they are sound and they
are what makes the problems above findable. Add, without modifying v0.3 code:

1. independent records per episode with position, distractor shape and wording as declared
   factors (`resolvelab.casedesk.world`, `manifest`);
2. an off-policy-safe teacher whose labels are verified by replay (`casedesk.teacher`);
3. grader v2 = v0.3 checks + escalation discipline + fault-exposure diagnostics;
4. a controlled training comparison that separates *more data* from *on-policy states*
   (DAgger vs a size-matched behaviour-cloning control), with seed- and record-level
   uncertainty reported separately.

The registered plan is in [casedesk-v2-protocol.md](casedesk-v2-protocol.md); its results
are in [artifacts/v0.4/RESULTS.md](../artifacts/v0.4/RESULTS.md).

## Counterfactual: the lookup follows the demo, not the reference

To test P3 directly, the three v0.3 test records were re-run with their contents and IDs
fixed and only the target's list slot moved (every slot, `plain` and `conflict+lost_ack`),
under the published prompt and under the same demo episode with its target moved to slot 0
(`scripts/diagnose_v03_position.py`; 300 episodes, exploratory, nothing selected on it):

| Arm | Demo target slot | Target slot 0 | Target slot 1 | Target slot 2+ |
|---|---|---:|---:|---:|
| base-0.6b | 3 (published prompt) | 0/6 | 0/6 | 0/18 |
| base-0.6b | 0 (counterfactual) | 0/6 | 0/6 | 0/18 |
| base-1.7b | 3 (published prompt) | 1/6 | 3/6 | 4/18 |
| base-1.7b | 0 (counterfactual) | 3/6 | 1/6 | 0/18 |
| lora-3407 | 3 (published prompt) | 0/6 | 6/6 | 18/18 |
| lora-3407 | 0 (counterfactual) | 6/6 | 6/6 | 0/18 |
| lora-42 | 3 (published prompt) | 6/6 | 6/6 | 18/18 |
| lora-42 | 0 (counterfactual) | 4/6 | 6/6 | 0/18 |
| lora-2026 | 3 (published prompt) | 2/6 | 6/6 | 18/18 |
| lora-2026 | 0 (counterfactual) | 6/6 | 6/6 | 0/18 |

All three adapters solve 54/54 later-page targets with the published demo and 0/54 when the
demo's target sits on page one; with the same weights and records, the demo's layout decides
whether the model pages on. The 1.7B base model shifts the same way. So the v0.3 adapters
learned "look where the demonstration looked", and record 6303 was the only test record that
exposed it. Cell counts and failure categories: `artifacts/v0.4/diagnostics/position-summary.*`.
